# 003：订单学习实验——数据准备、并发验证与性能观察

## 1. 目标、范围与当前状态

目标是通过可观察的实验理解：HTTP 与数据库之间怎样对应、事务如何回滚、行锁如何让请求等待、唯一约束如何处理重复请求，以及负载增加时延迟为什么变化。

本阶段用于本机学习，不测生产容量，不承诺某个 QPS，不要求监控平台、分布式压测或生产环境部署。优先用小实验解释因果，再做一次有界并发验收和小规模性能观察。

- 设计日期：2026-10-13。业务、接口和事务顺序以 `002-order-purchase.md` 为准。
- 初始设计交付只包含本文；当时没有创建实验脚本、修改应用、启动服务、操作数据库或执行实验。后续状态见第 8 节，脚本设计补充见第 7.1 节。
- 2026-10-15 读取代码确认：GET、Service.Create、Store 事务方法及 POST handler 已有实现，POST 不再是 501 占位。实际实验反馈见第 8 节；代码存在不等于全部 HTTP 边界已验收。
- 002 中已有 HTTP 生命周期测试、库存局部数据库实验和模拟 Go 分支验证，不等于下面的完整业务实验已完成。
- 执行时先重新核对实际代码、环境和最新记录。POST 未接通时，不能用 501 响应统计下单性能。纯 SQL 的 E04 可以独立学习；HTTP 下单实验先通过 E00、E01。

## 2. 实验方法与教学节奏

每次只推进一个小目标，约 60–90 分钟；不要求一次做完全部实验。

每个实验遵循：

1. 先说明它要回答的问题和相关机制，让学习者预测结果。
2. 明确测试商品、初始库存、请求键、请求次数、数量及并发方式。
3. 运行实验，保存每次请求的响应和耗时，区分新建、重放、业务拒绝和系统错误。
4. 等请求和事务结束，用新数据库查询核对订单、库存和唯一性。
5. 对比预期，解释异常；记录实际证据、局限和清理结果。

并发启动只代表请求可能重叠，不能保证恰好同时读库存。先做可控制的行锁实验，再做小规模竞争；关键小实验用新数据重复几轮。如果未观察到竞争，不能直接证明没有竞争问题。

本轮不故意删除唯一索引、移除锁或增加生产故障开关。若以后希望比较无保护版本，先单独补设计、隔离数据，再实验。

## 4. 数据隔离与公共验证办法

### 4.1 每轮数据约定

- 每轮取一个唯一 run_id，例如 `learn-20261013-a01`，仅使用 ASCII 字母、数字、`-`、`_`。
- 成功购买的新请求键使用 `<run_id>-r0001`、`r0002` 等；同键实验有意重复同一键。总长度不超过 64。
- 每个独立实验/重复轮次创建新的测试商品，名称含 run_id；记录实际生成的 product_id，不假设 ID 从 1 开始。
- 新测试商品默认 `is_active=true`，库存按各实验设置，初始订单数为 0；特殊数据另行说明。
- 每轮记录测试商品 ID 列表、初始库存、请求键列表、实际订单 ID。实验运行期间不让其他操作购买或改写这些商品。
- 除专门演示外部修改的实验，运行期间不补库存、不下架、不清理订单。否则库存核对公式的前提发生变化。
- 不 TRUNCATE 表、不重建整个库、不通过 down 删除业务表。只清理本轮明确记录的数据。

### 4.2 最小数据准备示例

下面是一个实验的准备模式。先把示例 run_id 替换为本轮唯一值，按实验设置库存；在同一 SQL 会话中执行并记录生成的 ID。

```sql
SET @run_id = 'learn-20261013-a01';
START TRANSACTION;
INSERT INTO products (name, is_active)
VALUES (CONCAT('learning-', @run_id), TRUE);
SET @product_id = LAST_INSERT_ID();
INSERT INTO inventory (product_id, available)
VALUES (@product_id, 3);
COMMIT;
SELECT @product_id;
```

这是测试数据准备，不是应用启动时的种子逻辑。SQL 用户变量属于当前连接；换连接后重新设置记录下来的 ID，不能默认 @product_id 仍存在。

### 4.3 必须记录的 HTTP 结果

| 结果 | 记录字段与含义 |
| --- | --- |
| 新建成功 | 201、replayed=false、订单 ID 和原始购买参数 |
| 已有结果 | 200、replayed=true、原订单 ID/参数/创建时间 |
| 业务拒绝 | 404/409 和具体 error.code；不能只按 HTTP 409 归类 |
| 输入拒绝 | 400/413/415 与 error.code |
| 系统或传输错误 | 5xx、客户端超时、连接断开、无效响应正文分别统计 |
| 时序 | request_id、发起/结束时间、耗时；不要逐请求打印敏感配置 |

测试正常业务时默认关闭客户端自动重试，避免改变请求总量。同键重试实验明确指定重试次数；不要把重试混进性能数字。

### 4.4 公共数据库核对

请求全部结束后，通过新的查询读取本轮数据。将 @product_id 设置为记录中的真实 ID：

```sql
SELECT available FROM inventory WHERE product_id = @product_id;

SELECT COUNT(*) AS order_count,
       COALESCE(SUM(quantity), 0) AS purchased_quantity
FROM orders WHERE product_id = @product_id;

SELECT request_id, COUNT(*) AS n
FROM orders
WHERE product_id = @product_id
GROUP BY request_id HAVING COUNT(*) > 1;

SELECT id, request_id, product_id, quantity, created_at
FROM orders WHERE product_id = @product_id ORDER BY id;
```

如果本轮有多个商品，对记录中的每个 ID 核对，并按完整请求键查 orders，确认没有意外落到别的商品。全局同键实验尤其不能只在单个商品下检查重复。

对于初始无订单、期间没有外部库存修改的独立测试商品，始终应满足：

```text
最终库存 >= 0
初始库存 - 最终库存 = 已提交订单 quantity 总和
每个 request_id 最多一笔订单
响应中的订单字段 = 数据库记录字段
```

订单数不能用自增 ID 的间隔计算，回滚可能留下 ID 间隙；必须查询实际记录。成功响应数也不是订单数，同一个订单可以被重放很多次。

客户端超时/断开不代表没有提交。记录发生不确定结果的键，等操作收敛后按键查库并用原键重试确认，不换键制造第二笔购买。出现超时先报告 HTTP 统计不满足预期，再单独核对数据库不变式；不能把异常算作库存不足而宣布通过。

### 4.5 清理

等待所有请求和事务结束后，按记录的测试商品 ID 精确删除相关 orders、inventory、products，可放在一个清理事务中。删除前核对商品名称和 ID 列表；多个商品按完整列表处理，缺失商品用例只检查对应请求键。
清理后用新查询确认本轮订单、库存行和商品行不存在，保留实验结果记录。不能靠请求键前缀误删其他数据。需要跨重启观察的实验先完成观察，再清理。

## 6. 每个实验的数据、步骤与验证

### E00：确认入口与环境

- 问题：请求是否真正经过 HTTP → Service → SQL，而不是命中占位代码？
- 数据：无须写业务数据；记录服务地址、数据库名称、迁移版本和代码版本。
- 操作：执行第 3 节检查；GET 非法 ID 应返回 400。核对 POST 实现和下单错误映射已经完成，再进入 E01。
- 验证：记录实际响应；若 POST 仍为 501，本轮停止 HTTP 下单实验，按 002 先完成接入。这里不执行大批请求。

### E01：正常下单、查单与重启

- 数据：新商品 P，active=true，库存 3；新键 R，quantity=2。
- 操作：POST 一次，保存订单 ID；GET 该 ID；重启订单服务后再次 GET。再查一个已确认不存在的 ID，以及非法文本 ID。
- 预期：POST 201/replayed=false；两次 GET 200 且字段一致；不存在 404；非法 ID 400。
- 数据验证：恰好 1 笔订单，quantity=2，库存 1；R 与响应 ID 对应；时间和参数一致。
- 学习点：只有一次成功提交
- 会留下持久数据，重启不删除订单。

### E02：输入和业务失败不能污染数据

每个用例使用独立商品/请求键，按表准备。失败后先查键无订单，再查对应库存未变。

| 用例 | 数据或输入 | 预期 HTTP/code | 库存与订单 |
| --- | --- | --- | --- |
| 非法购买参数 | 商品库存 3；quantity=0/-1、product_id=0、空键或非法字符分别请求 | 400 invalid_input | 库存 3，相关键无订单 |
| JSON 边界 | 库存 3；错误类型、未知字段、多个 JSON 值、缺失字段、根 null 等分别请求 | 400 invalid_input | 无业务写入 |
| 请求体过大 | 库存 3；Content-Type 正确，正文超过 4 KiB | 413 body_too_large | 无业务写入 |
| 类型不支持 | 库存 3；缺少或错误 Content-Type | 415 unsupported_media_type | 无业务写入 |
| 商品不存在 | 查询确认不存在的正 ID，quantity=1、新键 | 404 product_not_found | 无该键订单 |
| 商品下架 | 新商品 active=false，库存 3，买 1 | 409 product_inactive | 库存 3，无订单 |
| 缺库存记录 | 新商品 active=true，不创建 inventory，买 1 | 500 internal_error | 无订单，inventory 仍无行 |
| 库存不足 | active=true，库存 1，买 2 | 409 insufficient_stock | 库存 1，无订单 |

最后在“库存不足”的商品上，用同一个失败键改为买 1：应 201，订单 1 笔，库存 0。解释失败尝试没有占住已提交的 request_id，因此尚未绑定购买参数；成功后该键才绑定。这和成功订单改参数的冲突不同。

### E03：顺序重复、改参数与下架后重放

- 数据：新商品 P、Q，均 active=true、库存 3；一个新键 R。
- 操作：先用 R 买 P 的 1 件；再次提交相同请求；分别用 R 改数量为 2、改商品为 Q；最后下架 P，再重放原成功请求，并用新键购买 P。
- 预期：第一次 201；同参数重放 200/replayed=true；改变数量/商品均 409 request_conflict；下架后的原请求仍 200；下架后的新请求 409 product_inactive。
- 数据验证：只有 R 的原订单，订单 ID/created_at 不变；P 库存 2，Q 库存 3；下架新键无订单。
- 学习点：已有成功结果优先返回，重放不会重新执行购买判断。

### E04：用两个 SQL 会话直观看行锁

- 数据：新商品 P，库存 1；不创建订单。不依赖 POST。
- 操作：会话 A 开事务，按主键 SELECT available ... FOR UPDATE。A 保持事务不结束；会话 B 开事务，对同一行执行相同锁定查询。
- 观察：B 等待；A 执行 ROLLBACK 释放锁后，B 才读到 1；B 随后 ROLLBACK。
- 验证：两会话记录开始/返回顺序；有权限时可观察数据库锁等待信息。最终库存 1、订单 0，两个事务均结束。
- 对照：若 B 改为普通 SELECT，它可以读取已提交库存，不等于拿到了扣减所需的排他锁。
- 限制：本实验演示 MySQL 行为，不证明应用已经正确使用锁。不要把 B 的长等待误认为数据库坏了，也不要一直持锁不清理。

### E05：扣减后、提交前终止进程

- 数据：新商品 P，库存 5；新键 R，购买 2；只运行一个请求。
- 前提：能用调试器准确停在 Service.Create 的 DeductInventory 成功返回之后、Commit 调用之前。不修改业务顺序，不添加 HTTP 故障参数。
- 操作：请求在该位置暂停时，通过另一连接做普通查询，应仍看到库存 5 且查不到 R 的已提交订单；终止这个实验进程，等待数据库结束其事务，再重启服务。
- 验证：新查询仍为库存 5、R 无订单。客户端连接失败属于预期故障，不算一次成功下单。用原 R 再正常购买，应 201，库存 3、订单 1 笔。
- 学习点：事务可以看见自己的未提交修改；其他连接不能据此认为订单已成功。进程退出前没有提交，数据库要撤销订单和扣减。
- 局限：暂停过长可能先触发请求超时，需记录实际终止原因；若无法定位断点，暂记未执行。可先用手工事务演示扣减/插入后 ROLLBACK，但只能记为 SQL 演示，不能替代真实服务崩溃验收。

### E06：不同请求抢最后一件

- 数据：新商品 P，库存 1；两个不同新键 R1、R2，都购买 1。
- 操作：初步脚本按第 7.1 节在同一批次发起两个后台请求，保留每次响应和时序；不自动重试。用全新数据重复约 3 轮，不要求赢家固定。同批发起不保证服务端实际重叠；需要严格共同起点或分支证据时，先补协调机制设计。
- HTTP 验证：每轮一个 201，另一个 409 insufficient_stock；没有重放或意外 5xx。
- 数据验证：1 笔 quantity=1 的订单，库存 0；失败键无订单；公共不变式成立。
- 学习点：不同请求要竞争同一库存行；排队后需要读到最新库存，不能都认为还有一件。

### E07：同一个请求抢最后一件

- 数据：新商品 P，库存 1；20 次请求使用同一新键 R，同样购买 1。
- 操作：同时放行 20 次请求，每次保存订单 ID、replayed 和耗时；用新数据重复约 3 轮。
- HTTP 验证：一次 201，19 次 200/replayed=true；全部返回同一订单及创建时间；不能返回库存不足或请求冲突。
- 数据验证：R 全局只存在 1 笔订单，库存 0，quantity=1。
- 学习点：两次预查询可能都未找到，数据库唯一键仍能选出一个新建者；失败方回滚后查询并返回它的结果。
- 局限：如果实际请求没有重叠，可能全部走预查询重放，不能声称重复键分支已被触发。需要分支证据时用调试时序控制或以后设计的集成实验，避免为此自动扩展应用。

### E08：同键不同参数同时竞争

- 数据：新商品 P，库存 3；同一个新键 R，两个请求分别购买 1 和 2。
- 操作：同时发出两次请求；保存成功者的 quantity 和订单 ID。
- HTTP 验证：一个 201，另一个 409 request_conflict；谁成功不固定，不能预设一定买 1。
- 数据验证：R 只有一个订单，数量等于赢家；库存为 3 减赢家数量（2 或 1），不是两笔都扣，也不能退回初始库存。
- 可选对照：改为两个新商品、同键相同数量但不同 product_id，检查只扣赢家商品库存；单独记录这一轮的两商品数据。

### E09：库存 100，1000 次不同请求

- 数据：新商品 P，库存 100；1000 个不同新键，每次买 1。
- 操作：使用 20 个请求执行者，每个完成一条再取下一条，合计发出 1000 次；有界并发不是一次启动 1000 个请求。不自动重试。
- HTTP 验证：正常完成应为 100 个 201、900 个 409 insufficient_stock；响应总数与请求数对应，没有 200 重放、其他 409、传输错误或 5xx。
- 数据验证：100 笔订单、购买总量 100、库存 0；每键最多一单，失败键不应有订单。
- 记录：开始/结束、耗时和结果分类；出现超时先分析，不把 503 当库存不足。即使 HTTP 分布不合格，也继续核对并分别记录数据库是否仍正确。
- 学习点：规模增加后，正确性断言不变。本实验大部分请求会走库存不足路径，结果不是成功创建订单的容量指标。

### E10：小规模观察并发增加后的变化

- 问题：并发更多，是否一定更快？请求可能在哪里等待？
- 数据：三轮分别创建新商品，每轮库存 300、200 个不同新键，每次买 1。各轮不混入重放、下架或库存不足。
- 操作：只改变并发数，分别为 1、5、20；其余代码、连接池、请求内容、HTTP 连接复用设置保持相同。使用编译后的正常服务，不把带 race 的服务耗时混入比较。
- 正确性前提：每轮 200 个 201，200 笔订单，库存 100；有异常就记录，不能只挑最快成功响应计算整体结论。
- 指标：整轮耗时、每秒完成数、成功/错误分布，以及 p50/p95/p99。200 个样本的 p99 受极少数请求影响，只作观察，不当成稳定尾延迟结论。
- 本轮保持简单，不额外写预热请求；记录首批请求可能包含连接建立成本。后续若引入预热，其订单/库存影响必须单独计入，不能用错初始库存。
- 解释候选：当前池上限 5；同商品库存是热点行。可能出现池等待、锁等待或本机资源竞争，CPU 不高也可能延迟增加。没有证据不能直接认定瓶颈，更不能立即改连接池来得到好看的数字。
- 需要深入时再设计采集 sql.DB.Stats 的 WaitCount/WaitDuration、数据库锁等待或阶段耗时；本轮不要求监控平台。
- 不设最低 QPS 或生产延迟目标；没有明显差异也要如实记录。精力允许时重复一轮确认观察，不持续加压直到机器失去响应。

### E11：持锁触发请求预算耗尽

- 数据：新商品 P，库存 2；新键 R，购买 1；SQL 会话 A 先锁住 P 的库存行，保持事务，不修改库存。
- 第一轮对照：发出 HTTP 请求后，在其 5 秒处理预算内尽快释放 A；应 201，库存 1，订单 1 笔。观察请求耗时增加。清理后第二轮使用全新商品和键。
- 第二轮：A 保持锁，发出一条 HTTP 请求，客户端超时设为比服务预算长（例如 10 秒），等待服务返回；服务的 SQL 等待应最终取消，通常返回 503 storage_unavailable。确认返回后立即结束 A 的事务，不永久持锁。
- 数据验证：第二轮释放 A 并等事务结束后，新查询显示库存仍为 2、R 无订单；然后用原 R 正常重试，应 201、库存 1、订单 1 笔。
- 学习点：超时、取消、回滚和释放池连接是连续的行为；“一直等锁”不应该留下已经提交的半成品订单。
- 记录实际错误和耗时，不要求精确在 5.000 秒返回。若客户端先超时，或无法确认请求曾进入锁等待，记录为未达到预期实验条件，不冒充服务超时路径通过。

### X01（可选）：可售检查通过后商品下架

- 数据：新商品 P，active=true，库存 2；两个不同键 R1、R2，均买 1。
- 操作：R1 在 ReadProduct 已确认可售后、库存处理前暂停；另一 SQL 会话下架 P；在请求预算内继续 R1，再发出 R2。
- 预期：R1 可以 201；R2 返回 409 product_inactive；库存 1、仅 R1 一单。
- 证据：记录准确暂停位置和下架提交顺序。没有时序控制或暂停导致超时，本轮不能证明该规则。结束前恢复/清理本轮测试商品。

### X02（可选）：客户端忽略响应，再用原键重试

- 数据：新商品 P，库存 2；同一键 R，买 1。
- 操作：完成第一条请求，但在学习实验中有意不利用其返回结果；随后用 R 再请求，并按键查数据库。
- 验证：最终同一订单，库存 1、订单 1 笔，重放返回 200。
- 学习点：重试使用原键，不能换键购买第二次。
- 局限：这只是模拟客户端不知道结果；没有复现网络断开、Commit 确认丢失或提交失败。真实网络故障需要另行设计，不把忽略响应称为已验证 commit_unknown。

## 7. 工具、文件与依赖的边界

- 本轮新增文件仅为 `.agents/.design/003-order-learning-experiments.md`，职责是实验计划和结果记录。
- 业务实现继续按 002；本文不授权导师替学习者补完整 POST、自动修改事务或安装依赖。
- 执行基础实验可使用已有 HTTP/SQL 工具；确认它们实际可用，不默认已有 Node、k6、调试器等。
- 后续需要请求程序、SQL 文件或集成测试时，先在本文补充具体目录、文件职责、输入参数、输出结构、实现顺序和失败/清理方式，再由学习者手写。
- 并发程序需要有界并发、明确总量、唯一/同键模式、请求超时、异常收集和结束等待；不要不受控地创建无限请求，或丢弃异步错误。
- go test -race 用于检查被实际执行的 Go 内存竞争；它不证明 SQL 行锁和数据库唯一性。现有生命周期测试证据保留，后续只有新增/变更相关路径或必要验收时才重跑，不拿重复编译代替业务实验。

### 7.1 2026-10-15：E06–E09 请求脚本的渐进设计

本补充先约定工具职责，再由学习者实现；本轮导师不创建 SQL/请求脚本，不发送请求或操作数据库。已确认本机有 `/bin/bash` 与 `/usr/bin/curl`；读取到已有 `.learn/E01/add_data.sql`，保留学习者文件。

- 问题与取舍：手动顺序 curl 无法主动制造请求重叠；后台请求可用于小规模并发观察，但需要等待全部请求完成、独立保存结果，避免输出混杂和遗漏失败。此阶段先使用 Bash 编排 curl，不安装压测框架。
- 拟新增 `.learn/E06/add_data.sql`：只准备新商品和库存 1，事务提交后输出真实商品 ID。每轮修改为新的 run_id；不直接创建订单。E07/E08/E09 后续分别使用各自目录的 `add_data.sql`，库存为 1/3/100，职责相同。
- 拟新增 `.learn/E06/run.sh`：输入 `run_id`、正整数 `product_id`，目标地址默认 `http://127.0.0.1:8080`；生成两个不同键，数量均为 1；同批发起两个后台 curl，保存 PID 并逐一 wait。先实现这一小步，再逐个实验扩展；不一次生成全部脚本。
- 初步 E06 脚本采用同批后台启动，不能保证服务端请求重叠，也不宣称实现了严格共同起点。首次结果作为小规模观察；按 E06 用新数据重复约 3 轮。若需证明特定并发分支或严格共同放行，先补充协调机制设计，不能仅凭响应分布声称命中分支。
- 后续 E07/E08 的 `run.sh` 分别同批发起 20/2 个后台任务；前者同键同参数，后者同键但数量分别 1/2。E09 的 `run.sh` 使用最多 20 个常驻执行者，每个处理完一条再发下一条，按不重叠的序号分配合计 1000 个不同键；不一次创建 1000 个后台任务。
- 输出放在 `/tmp/flash-order-experiments/<run_id>/`，拒绝复用已有目录。记录本轮 run_id、商品 ID、初始库存、请求计划、代码版本及未提交变化、开始结束时间。每次 HTTP 尝试以独立序号命名输出，即使 request_id 相同也不共用文件。
- 每次尝试保存请求 JSON、发起/结束时间、响应正文、curl 标准错误、curl 退出码，以及 `--write-out` 输出的 HTTP 状态码和总耗时。curl 使用 `-sS --max-time 10 --retry 0`，不启用 `--fail`，以保留预期 409 的正文；脚本显式捕获非零退出码，不能因一条失败提前退出或丢掉其他在途结果。
- 结果分类区分 curl 传输错误、无效正文、201 新建、200 重放、不同 error.code 的业务拒绝和 5xx。不能只数退出码为 0 的请求，也不能把所有 409 当库存不足；元数据中的 HTTP 码不能掩盖 curl 超时或响应不完整。
- 实现顺序：准备 E06 数据并提交 → 手写单次 curl 的输出收集 → 两次后台启动及逐 PID 等待 → 人工核对两份响应 → 新查询核对第 4.4 节不变式并重复新轮次 → 分别扩展 E07/E08 → 最后实现 E09 的有界执行者和统计。自动汇总脚本若需新增文件，先补充其接口设计。
- 失败及清理：出现 5xx/超时也收集并等待全部尝试，保留原键，等服务端事务结束后按键查库；不换键自动补发。先保存证据，再按第 4.5 节精确清理本轮数据库数据，输出文件保留供记录；不自动删旧结果或清空数据库。
- 验收仍按 E06–E09 各节的 HTTP 分布与数据库断言分别判断；脚本应检查预期结果文件数与请求计划一致。文件可用 `bash -n` 检查语法；这不能代替真实 HTTP/MySQL 验收。
